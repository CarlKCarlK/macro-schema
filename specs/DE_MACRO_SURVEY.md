# Device Envoy Macro Migration Survey

<!-- TODO0 consider deleting this survey once the migration has shipped and the historical baseline is no longer useful. -->

This document records the completed `const-structures` declaration migration
in Device Envoy and the design choices made for that client. Device Envoy is a
substantial client and test corpus for the general-purpose framework, not its
compatibility target. The pre-migration macro survey was taken at `4c1ee16f`;
that baseline is summarized below instead of keeping its obsolete grammars.

## Current architecture

The framework lives in `/home/carlk/programs/const-structures`. Its schemas
live beside the Device Envoy code generators that consume them. Each public
schema uses `const_structures::define!`; this generates a thin macro wrapper
that forwards invocation tokens and schema data through `$crate` to the one
`expand!` proc macro. The framework parses and validates the declaration,
resolves defaults, normalizes optional fields and group members, creates
configuration documentation, then invokes the client-local generator.

The client crates re-export `expand!` once at crate root as
`__const_structures_expand`. Each generated wrapper is re-exported first by a
bare-name `pub use wrapper as public_name` in its definition scope. The hidden
wrapper is never reached through a crate path: rustc rejects absolute paths to
macro exports generated by macro expansion. `$crate` preserves references to
the client crate when dependencies are renamed. The `fixtures/demo` lint and
internal invocation, `fixtures/renamed-user`, and
`fixtures/alias-regression` exercise these details.

`define!` now has two generator forms. The explicit generator-path form keeps
supporting custom multi-arm backends. An optional trailing `generate { ... }`
instead takes ordinary `macro_rules!` output tokens and derives a single
matcher from the schema. That matcher is emitted as a hidden exported backend
with a bare-name alias in the schema's module; the final segment of the
generator path names that alias. Definition attributes such as `cfg` are
applied to the backend and alias.

Template bindings include root metadata (`$attrs`, `$vis`, `$name`, `$doc`),
root leaf values (`$field_FIELD`), nested leaf values
(`$field_BLOCK_FIELD`), and, for schemas with members, `$member_count` plus
member metadata (`$member_attrs`, `$member_vis`, `$member_name`, `$member_doc`,
`$member_index`) and leaf values (`$member_field_FIELD`, extended through
nested blocks). Optional fields/blocks and members follow `?` and `*`
macro-repetition nesting. Blocks are destructured into leaf bindings rather
than captured opaquely, and colliding flattened binding names are diagnosed.
The spec documents the full binding and normalization contract.

This is a prototype, not a wholesale Device Envoy migration to templates.
`examples/normalized.rs` demonstrates the template form, and RP `led_strips!`
now uses it to generate the normalized backend matcher. Its helper macros,
such as the per-member emitter, still implement domain-specific output. Other
Device Envoy declarations retain their explicit generator backends where that
form fits their generation needs.

Device Envoy's public RP and ESP schemas cover buttons, infrared declarations,
LCD groups and devices, LED devices and groups, audio players, and servos and
servo players. Core audio clip declarations `pcm_clip!` and `adpcm_clip!` also
use schemas. Client generator macros still own the emitted structs, statics,
tasks, methods, and implementation helpers. Some generators intentionally
create private helper items and synthetic groups; the schema framework does
not generate those domain types or require them to be public.

ESP LED strip and panel generators now emit the caller-named struct directly
with its attributes, visibility, and documentation; hidden inner types and
public type aliases were removed. All LED animation schemas use
the shared `MAX_FRAMES_DEFAULT` value with a `default_display` spelling for
user-facing docs. The ESP `led2d!` generator normalizes engine selection
through a shared capability-aware dispatcher. These are client generator and
schema decisions, not framework rules. The removed
`__validate_keyword_fields_expr!` helper is not part of the current design;
schema expansion handles field validation.

## Migration scale and remaining handwritten macros

Approximate macro-source comparisons from the migration:

| Area | Before | After or additions |
| --- | ---: | ---: |
| RP LED macros | 2,716 lines | 469 lines, plus adjacent schemas |
| ESP IR macros | 1,689 lines | 440 lines |
| ESP LED macros | 1,427 lines deleted | 162 lines added for schemas and dispatch |

These figures describe macro implementation source, not whole-crate size.
Remaining handwritten macros include `tone!`, `combine!`, `tga!`,
`init_and_start!`, and internal implementation helpers. They remain outside
this schema migration.

## Device Envoy choices

These choices regularize Device Envoy declarations; another framework client
may choose different field names and semantics:

- Shared group fields are inside the group braces. Members use `Name { ... }`
  and fields use `name: value`.
- Declarations accept any field order, an optional trailing comma, and outer
  attributes. Members inherit group visibility; an explicit member visibility
  is rejected.
- Device Envoy schemas have one spelling for each field and use named `servo!`
  declarations on RP and ESP.
- Each schema owns its field kinds, defaults, optional values, and constraints.
  Similar fields such as `max_frames` and `max_steps` need not have identical
  meanings or defaults across APIs.
- Device Envoy generators own hardware-specific behavior: peripheral types,
  resource claims, member-derived defaults, emitted item visibility, and
  hardware capability dispatch.

## Baseline and migration findings

The survey at `4c1ee16f` found inconsistent declaration forms: some groups put
shared fields before the name, group members used `Name: { ... }`, field order
and trailing-comma rules varied, attributes and visibility were accepted
inconsistently, and RP and ESP `servo!` had different shapes. Defaults and
field meanings also varied between otherwise related macros. These were
migration inputs, not framework compatibility requirements.

Migration verification found two environment/configuration issues. The
embedded test runner searched the wrong directory, so the embedded tests had
not run. The Xtensa linker received `-Tlinkall.x` twice because both the root
and crate Cargo configurations supplied it. These are repository validation
and linker-configuration issues; the migration did not identify duplicate
resource symbols as a framework defect. The follow-up also fixed panel engine
dispatch: default panels now select SPI on chips without RMT, and explicit
RMT requests go through the shared capability check.

The framework and migration fixture layout is documented in
[CONST_STRUCTURES_SPEC.md](CONST_STRUCTURES_SPEC.md). The old per-macro
baseline grammars and matcher-by-matcher inconsistencies are intentionally not
maintained here now that the migration is complete.
